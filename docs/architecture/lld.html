Low-Level Design (LLD) & Component Blueprint

This Low-Level Design document specifies the concrete code structures, entity contracts, MediatR CQRS commands, domain sorting algorithms, EF Core JSONB schemas, and state management stores that power Vedha AI.

💡 Plain-English Summary: What is LLD?

If High-Level Design (HLD) is the strategic city map showing how highways and districts connect, Low-Level Design (LLD) is the precise architectural blueprint for each building. It defines the exact C# classes, database fields, algorithmic sorting rules, and JavaScript state stores so any engineer can modify or debug any feature without guessing.

1. Low-Level Design Overview & Request Pipeline

Vedha AI's backend is structured strictly around Uncle Bob's Clean Architecture. Every incoming HTTP request flows through a unified MediatR CQRS pipeline that enforces authentication, input validation, execution, and deterministic data transformation before persisting to PostgreSQL.

3. Deterministic Experience Chronology Engine (ADR-003)

Recruiters require that a candidate's current employment always appears first on a resume. Because generative LLMs occasionally violate chronology when chasing keyword density, ExperienceChronologyHelper enforces reverse-chronological order deterministically in code. 

// Location: backend/src/ResumeTailor.Domain/ValueObjects/ResumeSchema.cs
public static class ExperienceChronologyHelper
{
    public static bool IsPresentRole(ExperienceItem item)
    {
        if (item.IsCurrent) return true;
        if (string.IsNullOrWhiteSpace(item.EndDate)) return false;
        var end = item.EndDate.Trim().ToLowerInvariant();
        return end.Contains("present") || end.Contains("current") || 
               end.Contains("now") || end.Contains("ongoing");
    }

    public static List<ExperienceItem> SortExperiences(IEnumerable<ExperienceItem> items)
    {
        return items
            .OrderByDescending(x => IsPresentRole(x) ? 1 : 0) // Primary: Present roles unconditionally 1st
            .ThenByDescending(x => IsPresentRole(x) 
                ? ParseFlexibleDate(x.StartDate)               // Current: Most recently started current role
                : ParseFlexibleDate(x.EndDate))                // Past: Most recently ended role first
            .ThenByDescending(x => ParseFlexibleDate(x.StartDate))
            .ToList();
    }
}

5. EF Core Persistence & JSONB Mappings

ApplicationDbContext configures PostgreSQL with Npgsql.EntityFrameworkCore.PostgreSQL. The entire ResumeSchema is mapped directly to a native PostgreSQL jsonb column for maximum query performance and schema flexibility. 

// Location: backend/src/ResumeTailor.Infrastructure/Persistence/ApplicationDbContext.cs
builder.Entity<MasterResume>(b =>
{
    b.HasKey(x => x.Id);
    b.Property(x => x.Title).HasMaxLength(200).IsRequired();
    // Maps C# value object to PostgreSQL native jsonb
    b.Property(x => x.Schema).HasColumnType("jsonb").IsRequired();
    b.HasOne<User>().WithMany().HasForeignKey(x => x.UserId).OnDelete(DeleteBehavior.Cascade);
    b.HasIndex(x => x.UserId);
});

builder.Entity<RefreshToken>(b =>
{
    b.HasKey(x => x.Id);
    b.Property(x => x.Token).HasMaxLength(256).IsRequired();
    b.HasIndex(x => x.Token).IsUnique();
    b.HasOne(x => x.User).WithMany(u => u.RefreshTokens).HasForeignKey(x => x.UserId);
});

6. AI Orchestrator & Truth Invariant Verifier (ADR-005)

RagResumeGenerator and AtsScoringEngine enforce truth preservation before persisting tailored resumes. The engine extracts quantitative metrics using regular expressions and verifies that no unearned claims exist.

Regex Metric Extractor

Scans text with pattern @"(\d+[\.,]?\d*[%$xXkKMmB]|\$\d+)". Extracts currency figures ($100k), percentages (24%), and scale multipliers (3x). If a tailored bullet contains an unverified metric, it triggers remediation.

Selective Bullet Rollback

Instead of aborting generation or failing the user's request, the invariant verifier automatically reverts the single violated bullet point to the candidate's verified master resume version.

8. Chrome Extension Manifest V3 Internals

The extension operates across decoupled execution contexts with resilient event communication:

Content Script Relay (content.js)

Injected into http://localhost:3000/* to listen for authentication postMessages, and into job portals (LinkedIn, Greenhouse, Lever, Ashby, Workday, Indeed, Naukri) to extract specifications and execute biometric form auto-filling. Enhanced scraper heuristics support modern LinkedIn containers (#job-details, .jobs-description-content__text, article.jobs-description__container) and dedicated Workday selectors ([data-automation-id='jobPostingHeader'], [data-automation-id='jobPostingDescription']), with OpenGraph and JSON-LD fallbacks. Safe auto-fill pairs questions with labels via extractFormQuestions, dispatches React synthetic events using descriptor prototype setters and _valueTracker resets, and retains z-index 2147483647 to float above modal dialogs.

Background & Popup Orchestrators (background.js & popup.js)

Coordinates chrome.storage.local state, manages AUTH_STORAGE_KEYS including vedha_refresh_token, and transparently refreshes expired access tokens via POST /api/auth/refresh before showing unauthenticated views. Tab messaging features dynamic timeout budgets (60,000ms for multi-step autonomous actions; 3,000ms for operational pings), preventing premature failure during humanized keystroke delays. Header actions feature a dedicated Side Panel launcher triggering chrome.sidePanel.open() alongside the in-page screen pin.

LinkedIn screening question flow

Employer questions such as “years with PostgreSQL”, “commute to Bangalore”, and “valid B1 visa” are not contact fields. The filler walks up to the nearest shell that contains a single control (or one radio group), reads the legend or .artdeco-text-input--label, and never reuses the first label on the step. Answers at confidence 0.8 or higher are typed with 15–35ms keystroke jitter or selected with pointer movement. Lower confidence draws an amber outline and a “Please review” badge. Invented defaults (5 years, 30 days, 140000 salary, sponsorship “No”) are not inserted.

Gemini Model Fallback Cascade & Transient 500 Resilience

In GeminiFunctionCallingClient.cs and AiProviders.cs, model resolution defaults to frontier flash models and dynamically cascades through gemini-2.5-flash → gemini-2.0-flash → gemini-1.5-flash → gemini-flash-lite-latest upon receiving HTTP 404 (NotFound), 400 (thought_signature validation), or transient HTTP 500/502/503/504/429 server errors with exponential backoff. Function call parts preserve Gemini 2.5/3.x cryptographic thoughtSignature tokens at the part level, guaranteeing 100% resilience against model deprecations and strict multi-turn tool loops.

Extension Step Fingerprint Auto-Remediation & Escalation

In extension/content.js, multi-step portal loops dynamically compute DOM element count, type, and field hash signatures. If a step fingerprint remains unchanged after clicking Next, the extension grants a 1000ms transition grace period, actively scans for unselected radio groups or missing required inputs, runs autonomous error remediation, re-clicks Next, and falls back to amber visual highlighting and graceful escalation if human input is mandatory.

Aksh Dynamic Skill Architecture, Input Elicitation & Domain Guardrails

In IAkshSkill.cs and AkshSkillRegistry.cs, Aksh operates as an All-in-One AI Career Operating System with 7 modular skills: PlatformNavigatorSkill, ResumeOptimizerSkill, InterviewCoachSkill, JobApplicationCopilotSkill, SalaryNegotiatorSkill, ProfileAndQueueAuditSkill, and CareerStrategistSkill. At turn initialization, intent is matched dynamically and streamed via SSE (skill event). When a user requests workflows such as resume tailoring, mock interviews, or offer negotiations without prerequisite data (e.g. missing Job Description or offer breakdown), Aksh engages **Proactive Input Elicitation**—acknowledging verified master profile facts and actively requesting the JD text or job link rather than failing or guessing. Strict **Domain Guardrails** constrain Aksh exclusively to Vedha AI features and user career data, declining off-topic queries. Multi-turn conversation history retains both user and assistant interactions across a 14-turn sliding window with pre-injected candidate grounding context.

Chat-First Copilot Experience & In-Chat PDF Generation

In AskAkshPage.tsx and AkshTools.cs, the rigid 3-field "Goal" form was eliminated in favor of a conversational-first interface (ChatGPT/Claude style). Submitting a prompt automatically initializes a session with instant streaming. Theme Toggling Decoupling & 3-Reference Aesthetic System (2026-10-15 Night)

Root Cause Diagnosis: Theme toggling appeared broken because high-level layouts (AppLayout.tsx, index.html, and index.css) contained hardcoded dark backgrounds (#09090b, #0c0d10) without responsive dark: variant fallbacks. When users toggled to Light mode, the dark class was removed from documentElement, but the hardcoded dark surface styles persisted.

Architectural Resolution:

  • Zero-FOUC Theme Pre-Hydration: Integrated synchronous head script in frontend/index.html inspecting localStorage.getItem('vedha_theme') before rendering, ensuring instantaneous synchronization without layout flash.
  • Coordinated DOM Synchronization: Upgraded useThemeStore in useAuthStore.ts to synchronously toggle both .dark and .light class tokens across both document.documentElement and document.body.
  • Reference 1 Integration (High Conversion Landing): Implemented 6-card multi-pastel architecture (Mint, Sky Blue, Lavender, Peach, Buttercup, Rose) featuring squircle dual-icon badges, high-contrast monospace metrics, and micro-metric status pills.
  • Reference 2 Integration (Autumn App): Warm aesthetic canvas (#FAF8F5), personalized hero spotlight banner ("Welcome back, Alex 👋"), and verified candidate profile card with avatar squircle, verified checkmark badge, and rapid status metrics.
  • Reference 3 Integration (Premium Flowbase): Segmented pill controls (All Applications / Queue / Interviews), dark translucent search pill with magnifying glass, rounded-full high-contrast action CTAs, and refined activity table.

Chat History Hydration, Real-Time Agent Telemetry & Past Resume Deserialization (2026-10-15 Late Night)

Root Cause Diagnoses:

  • Chat History Loss: In AskAkshPage.tsx, switching sessions invoked setThread([]) and never synchronized messages from akshApi.getAudit(sessionId). Additionally, AkshAgentRunner.cs capped message summaries at 2,000 characters with \n…[truncated], corrupting longer LLM answers upon database round-trip.
  • Agent Execution Opacity: While Aksh performed background steps (URL scraping, requirement extraction, package preparation), the UI rendered only a generic loading screen ("Aksh is reasoning...") without granular stage progression.
  • Past Resume Preview Deserialization: In TailorCommands.cs, JsonOptions lacked PropertyNameCaseInsensitive = true. Because OrchestratorCommands.cs serialized TailoredStructuredJson with standard C# PascalCase naming, deserialization in GetTailoredResumeByIdQuery silently dropped all properties, returning empty experiences, skills, and personal information.

Architectural Resolutions:
  • Serialization Case-Insensitivity: Unified JsonOptions across TailorCommands.cs, OrchestratorCommands.cs, and ToolCommands.cs with PropertyNameCaseInsensitive = true and camelCase policy. In GetTailoredResumeByIdQuery, added fallback queries for master resumes and on-the-fly ATS score recalculation.
  • Defensive Schema Null-Safety: In ResultStudioPage.tsx, wrapped masterSchema, tailoredSchema, and atsAnalysis arrays with safe optional chaining and fallback empty arrays, completely eliminating undefined property runtime crashes.
  • Granular Multi-Step Telemetry: In AkshAgentRunner.cs, emitted discrete SSE status events (ScrapingJob, TailoringResume, Reasoning, PackagePrepared). Increased MaxSummaryChars to 64,000 to preserve full conversational guidance.
  • Rich Live Progress Widget & History Hydration: Upgraded AskAkshPage.tsx with a real-time progress card (dynamic stage badge, pulsating accent line, and human-readable detail beside /assets/loading.gif) and automated message hydration upon session selection via akshApi.getAudit.

Decision Engine Architecture & Technical Exploration: Jev vs. Free Competitors

Investigation Objective: Evaluate TypeSafe AI's Jev and identify free, open-source competitors for sub-second, zero-cost decision making and agent routing across the ResumeBuilder / Aksh AI pipeline.

1. What is Jev?
Developed by TypeSafe AI (founded by Diogo Almeida, co-author of OpenAI's InstructGPT), Jev is a non-autoregressive discriminative model specifically designed for AI agents. Rather than generating text tokens autoregressively (which is slow, expensive, and prone to hallucination), Jev takes structured JSON state and questions, outputting:

  • Noul: Binary Yes/No boolean decision with calibrated log-odds.
  • Score: Numerical value [0–100] with standard error calibration.
  • Choice: Multi-class categorical selection across predefined enum candidates.
Pricing & Availability: Proprietary, cloud-only, closed-source API billed per evaluation. Not free.

3. Recommended Architecture for ResumeBuilder & Aksh AI:
Implement a 3-Tier Hybrid Decision Pipeline:
  • Tier 1 — Deterministic Business Guardrails (< 1ms, $0): Use Zen Engine for daily dispatch limits, salary threshold checks, blacklist company filters, and minimum ATS cutoff checks.
  • Tier 2 — Semantic Routing & Tool Selection (50ms, $0): Use Outlines with a local lightweight SLM (Qwen 2.5 1.5B / Llama 3.2 1B) for schema-constrained logit masking (guaranteeing 100% valid tool names, skill choices, and boolean dispatch triggers without generating runaway prose).
  • Tier 3 — Deep Generative Reasoning (1–2s, Gemini/Claude): Reserve full autoregressive LLMs exclusively for nuanced resume bullet synthesis, cover letter copywriting, and complex mock interview coaching.

Section 13 • UI/UX Architecture

Universal Light/Dark Theme Decoupling & Token Architecture

Decoupling all application surfaces from hardcoded pitch-black styling (#111216, #16181f, #121215) and establishing an adaptive, dual-token design system consistent with the Autumn App aesthetic.

1. Architectural Defect & Root Cause Analysis

While the initial design system overhaul established adaptive variables at the root layout, seven core sub-pages continued to use un-prefixed Tailwind arbitrary classes (e.g., bg-[#111216] and text-white). Because Tailwind treats un-prefixed rules as default (Light Mode) declarations, clicking the theme toggle correctly transitioned the canvas to warm cream (#FAF8F5), but cards remained jet-black with white text.
