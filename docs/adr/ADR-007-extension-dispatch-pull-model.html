ADR-007 — Backend-to-Extension Dispatch

ACCEPTED 2026-10-10 Phase 4 Supersedes: log-only copilot staging
Plain English: approving an application used to end at “staged for review” — words in a log, with no browser ever opening the form. Now an approval dispatches the run: your browser extension notices it within a minute, claims it (so only one device ever runs it), fills the real portal in your own logged-in tab, and reports every step back. If your laptop is closed, the run waits honestly and becomes retryable on its own. Nothing ever claims success without a receipt.

1. Context

The copilot pipeline (JobApplicationOrchestrator → providers) ends its copilotReviewMode branch with PausedForUserReview plus log copy. The extension owns a working observe→fill→verify→fix harness (runAutonomousMultiStepFill), but the two halves never met: the backend has no channel into the candidate's browser, and the extension never learns a backend run exists. The spike (bugfix doc v1.0–v1.7) already established extension-first execution as the ban-safe posture — dispatch is the missing link that makes it real.

2. Decision — claim-based pull, not server push

1
Dispatch. A successful paused copilot run becomes DispatchedToExtension (new enum value = 7, appended only) when Dispatch:Enabled. Finalize runs and worker failures never dispatch.
2
Poll. The extension service worker fires a 60 s chrome.alarms tick (new alarms permission) and asks GET …/extension/runs/next with its existing JWT. 204 = nothing waiting.
3
Claim (atomic). The first claimant wins via an ExtensionRunClaims ticket whose PK is QueueItemId — one live claim per item on every database, no raw SQL, no provider-specific GUID handling. Losers get 204 and move on.
4
Execute. The poller opens/focuses the posting tab, drives the existing harness, and maps its result to receipts: started → step* → paused | submitted | failed | cancelled.
5
Receipts. POST …/runs/{id}/receipt appends logs, advances queue + Aksh session state, and doubles as a heartbeat refreshing the 10-minute lease. Terminal receipts are idempotent; stale tokens get 409; cancelled/foreign runs get uniform 404.
6
Lease sweep. A BackgroundService releases claims older than 10 minutes back to dispatchable (terminal/cancelled runs are never resurrected). Tracker cancel blocks claims and aborts in-flight steps.

3. Alternatives considered

OptionVerdictWhy
SignalR push to extensionRejectedMV3 service workers are killed after ~30 s idle — no persistent socket survives. The backend already pushes progress to the SPA over SignalR; the extension never adopted it, and adopting it means a reconnect/backoff subsystem for zero benefit over polling.
Raw-SQL atomic UPDATE…WHERE claimRejectedGUID parameter handling differs between Npgsql (native uuid) and SQLite (TEXT, driver-dependent format). The ticket-PK design gets atomicity from constraints instead of SQL text, and is covered by a race test on SQLite.
EF concurrency token on the queue rowRejectedA [ConcurrencyCheck] rides every UPDATE of the row, so all existing flows would need DbUpdateConcurrencyException handling — a regression surface far larger than the feature.
Hangfire recurring sweepDeferredNo Hangfire server exists anywhere in this tree (only dashboard env keys). A BackgroundService on the existing hosted-service pattern does the job with zero new packages. Revisit if job volumes demand durable scheduling.
Provider-side dispatch branchesRejectedEvery portal with a copilot branch is extension-runnable, so capability is uniform. The orchestrator-side predicate (ShouldDispatchToExtension, matrix-tested) keeps all 7 providers untouched and test-compatible.

4. Consequences

Positive

  • “Staged” becomes genuinely filled applications with per-field receipts; every gate fails closed with honest copy.
  • Additive only: 1 enum value, 2 columns, 1 table, 1 index, 2 endpoints, 1 flag — zero existing contracts changed, rollback is flag-off.
  • Multi-device safety and crash recovery fall out of the lease design rather than new code paths.

Costs & risks accepted

  • 60 s poll latency per run (alarm floor) — acceptable for a human-supervised flow; claim is instant once polled.
  • Extension update prompts for the new alarms permission — noted in release notes.
  • File-upload portals report failed/upload_unsupported in v1 rather than faking success; upload-capable packages are the defined v2.
  • Tracker “Applied” sync reuses the standard submitted path; extension-path analytics (claim latency, fill rates) are v2.
Verification at acceptance: 115/115 unit tests green (18 new dispatch tests incl. race, idempotency, IDOR, sweeper), backend build 0 errors, frontend build green, extension node --check clean, worker py_compile clean.
