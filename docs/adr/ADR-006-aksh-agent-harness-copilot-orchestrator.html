Aksh — Agentic Copilot & Harness Orchestrator on Microsoft Agent Framework

Introduce Aksh: a single conversational AI agent that plans, executes, and supervises the entire Vedha AI copilot pipeline — job scraping, resume tailoring, cover letters, screening answers, queue preparation, and browser submission — built on Microsoft Agent Framework (MAF) 1.24.0 and its batteries-included Harness Agent. This ADR answers: can we implement it, how does it work, and what does it change? Short answer: yes — as a thin agentic layer over the existing MediatR pipeline, behind the existing Review Gateway.

💡 Plain-English Summary: What Is Aksh?

Today the candidate clicks through separate stages: paste a job link, tailor the resume, generate a cover letter, answer screening questions, review the queue item, then launch browser automation — like ordering each course of a meal from a different waiter. Aksh is one head waiter (think Naukri's Neo agent): you say "Apply to this LinkedIn posting", and Aksh breaks the job into a todo list, calls the existing kitchen (scraper, tailor, Q&A engine, ATS truth-checker), shows you every draft for approval, and only then walks the finished tray to the browser. It never invents facts, never submits without your explicit approval, and writes down everything it did so you can audit it.

1. Context & Problem

The current orchestrator (JobApplicationOrchestrator.RunPipelineAsync) is an imperative pipeline: fixed steps in a fixed order, driven by button clicks. Each AI call is one-shot with no run memory, no plan, no recovery, and no clarifying questions mid-flow. The connected spike (docs/bugfixes/copilot-pipeline-auto-apply-stall-and-extension-harness-spike.md) proved a harder fact: the pipeline stages but never applies — providers return PausedForUserReview with log lines only, and the headless worker fallback degrades silently. Aksh is the strategic answer; the spike is the tactical build plan. Neither duplicates the other.

  • No run-level reasoning: cannot re-plan when a step fails (scraper blocked → ask for pasted JD text).
  • No conversational surface: cannot hold a goal like "get me ready to apply to these 3 jobs".
  • No execution venue strategy: headless-first is both fragile and ban-prone; the spike inverts this to extension-first.
  • Hand-rolled scaffolding risk: loop, memory, approvals, telemetry from scratch duplicates supported MAF runtime.

2. Decision

Adopt Microsoft Agent Framework 1.24.0 (verified 2026-10-10; GA since April 2026, monthly cadence, 11M+ downloads, net8.0 target → runs on net10.0, built on Microsoft.Extensions.AI 10.x) and build Aksh as a Harness Agent (chatClient.AsHarnessAgent(...)) whose tools are thin adapters over the existing Vedha pipeline. The harness supplies the runtime (tool loop + iteration cap, todos + plan/execute modes, session memory, compaction, approvals, web search, OpenTelemetry); Vedha supplies domain tools and guardrails (ATS truth engine, Review Gateway, per-user scoping, pacing governor).

4. End-to-End Flow & Sequence

1
Goal intake (chat)

Candidate types "Prepare my application for <job URL>" in SPA or extension. WebApi opens a per-user AkshSession (status Planning) and streams the run over SSE + SignalR.

2
Plan mode → visible todo list

scrape JD → tailor resume → truth-check → cover letter → screening answers → queue package → supervised apply. Candidate can edit/reorder before execution starts.

3
Execute via typed tools (never raw prompts)

Each step calls an AIFunction adapter delegating to existing MediatR handlers (DetectJobSourceQuery, tailoring chain, GenerateScreeningAnswersCommand, PrepareApplicationPackageCommand). L0 deterministic shortcuts run first, zero tokens.

4
Blocking truth gate

check_truth runs IAtsScoringEngine.ValidateTruthPreservation locally. Violation → safe fallback to master bullets + audit entry. Not skippable by the model.

5
Human approval (Review Gateway)

Queue item presented with diffs + answers. launch_apply pauses the run; on approval, ExecuteApplicationQueueItemCommand runs through the extension-first executor (spike §4). Same PausedForUserReview → Submitted states.

6
Memory + audit + ledger

Scratch notes in session file-memory; durable facts to Postgres/pgvector; todos + tool receipts + approvals persisted; input/output tokens metered into the session ledger.

8. Extension Harness Loop (Observe→Fill→Validate→Fix)

Aksh's launch_apply executes primarily through the extension run-session in the candidate's own logged-in browser (genuine TLS/IP/fingerprint/session — the lowest ban surface per 2026 detection research); the headless worker is fallback only. Full design lives in the connected spike; the contract here:

O
Observe

Snapshot field descriptors (label/type/options/required/validation state) — no PII in transit beyond values being filled. Reuses SemanticDomFormMapper semantics in-page.

F
Fill (human-like)

Focus → char-by-char typing with jitter → blur → input/change events (extends setNativeValue); custom dropdowns via open→search→select→verify; uploads verified by widget state.

V
Validate

findActiveValidationErrors re-scan + MutationObserver for async badges (covers Workday AJAX wizards); per-step receipts, never assumed success.

X
Fix (budgeted)

Deterministic normalizers first, AI re-query for semantic rejects, ≤3 retries per field, then escalate with highlight. EEO/consent fields are never guessed.

9. Alternatives Considered

A. Hand-rolled agent loop (rejected)

Full control, but re-implements planning, compaction, approvals, telemetry — the shipped MAF runtime. Highest maintenance.

B. Python-side agent (rejected for now)

Pipeline, auth, and data live in .NET; a Python agent duplicates contracts and crosses a process boundary per tool call.

C. MAF HarnessAgent in .NET (selected)

Supported runtime, in-process tools over existing handlers. We configure the harness; we own tools + guardrails.

D. Do nothing (rejected)

Click-path bottleneck grows with every ATS adapter; stall root cause (spike) remains; no Neo parity.

⚠️ What Aksh Deliberately Does NOT Copy from "Neo-style" Agents

Unattended auto-submission. Preparation is aggressive; submission is conservative — every application passes the Review Gateway and explicit approval. Anti-ban (spike §3) and correctness (a wrong answer at machine speed is worse than none).

10. Security & Prompt-Injection Defense (deterministic-first)

Injection is the #1 OWASP LLM risk: a posting can hide "ignore previous instructions…" in scraped text. A defensive system prompt alone is rejected as insufficient. Two layers:

Layer 1 — FIDES information-flow control (framework)

Integrity (trusted/untrusted) + confidentiality (public/private) labels on every content item; label-tracking middleware propagates the most restrictive label; policy middleware blocks — or routes to approval — sensitive tools invoked from untrusted context before execution. Untrusted blobs auto-hide behind variable references, processed only by a tool-free quarantined model. Mapping: JD text → untrusted; profile/resume/memories → trusted; launch_apply refuses untrusted context (violations → Review Gateway); PII context capped from public sinks. Phase 0 confirms the .NET surface (docs skew Python); else Layer 2 stands alone.

Layer 2 — Vedha deterministic controls (hold regardless)

  • Data-vs-instructions: JD text only as delimited data args; chat stays user role, never system.
  • Quarantine parse: isolated tool-free extraction; only validated JobDescriptionSchema JSON re-enters context.
  • Allowlist: named Vedha tools only; no shell/file/network in the server harness.
  • Truth gate as security gate: injected fabrications fail closed to master bullets.
  • Side-effect gating: only launch_apply, post-approval, idempotent, logged.
  • Isolation + secrets: per-UserId sessions/memory/keys; IEncryptionService; .env never committed; output sanitized before render.
Data sourceLabelMay driveMay never drive

11. Cost-Efficient History & Token Discipline

History storage and history reasoning are separated — the key pays for reasoning, never remembering. Verified 2026-10-10: Flash-Lite ≈ $0.25/M input, $1.50/M output, cached reads ≈ $0.025/M, Batch ≈ 50% off.

L0 — Deterministic (zero tokens)

Profile/memory-hash hits, truth invariants, validation regexes, audit rows. L0 runs before any LLM call.

L1 — Hot session (zero tokens)

Turns + run state as Postgres rows, re-read from DB; transcripts never re-sent as reminders.

L2 — Warm summaries (cheapest model)

Flash-Lite compaction keeps receipts (hash + output); blobs referenced by ID, not pasted.

L3 — Cold semantic (embed once)

One embedding per artifact hash; local vectorizer fallback free; retrieval top-k only.

Worked example — one full application ≈ $0.01

JD schema      ~3.0k in / 0.5k out (lite)   ≈ $0.0015
Tailoring      ~8.0k in / 2.0k out (lite)   ≈ $0.0050
Cover letter   ~4.0k in / 0.6k out (lite)   ≈ $0.0019
Answers+fixes  ~3.0k in / 1.0k out (lite)   ≈ $0.0023
Summary/plan   ~1.0k in / 0.3k out (lite)   ≈ $0.0007
TOTAL ≈ 19k in / 4.4k out  ≈ $0.011  →  repeat applications ≈ $0 via memory-hash hits
  • Routing: Lite for extraction/Q&A/summaries/fix-loops; Pro-tier only for STAR synthesis + cover letters; thinking budget 0.
  • Cost-ordered failover: same-provider retry first; cross-provider only on quota failure.
  • Ledger: usageMetadata per call → per-application/day spend, pause on breach, "this application cost $0.011" in UI.
  • Batch + cache on math: nightly consolidation via Batch; context caching only past ~3–4 reads/hour break-even.

14. Risks & Edge Cases

  • FIDES .NET parity — RESOLVED Phase 0: zero FIDES surface in MAF .NET 1.24.0 packages → Layer-2-only design locked; re-check at each MAF minor bump.
  • Conservative labels: once-untrusted context stays untrusted → approval UX must explain why (Phase 2 copy work).
  • Portal drift (LinkedIn/Workday DOM changes) → field-descriptor snapshots versioned; mapping failures escalate, never guessed.
  • Ban surface on L3: opt-in per portal, governor-enforced; LinkedIn stays L2-only permanently.
  • Cost overrun: ledger + budgets + kill switch; Batch consolidation is offline-only.
  • Stale plans: JD or profile changed mid-run → re-plan prompt, never silent continuation.

17. MCP Remote Tool Plane (Adopted Direction)

Decision (user-agreed 2026-10-10): expose Vedha capabilities over the Model Context Protocol as the remote tool plane — with one correction on scope. In-process AIFunction adapters stay for hot, DB-bound tools (sub-millisecond, shared request transaction, free ASP.NET auth). MCP wins where the tool lives elsewhere, and it additionally lets external agents (Claude Desktop, Foundry agents, user scripts) drive Vedha.

Phase 3b — Worker tools over MCP

Replace the bespoke /api/playwright/* REST with MCP tools (observe_dom, fill_field, verify_form, submit_application) over Streamable HTTP; Aksh consumes them via MAF's MCP client. Same catalog, same approval gates, standard transport.

Phase 4 — Public Vedha MCP server

External clients drive prepare/answer/queue flows with per-user bearer auth. Strategic unlock: Vedha as a tool provider, not just an app.

  • Non-negotiables carry over: per-user scoping (bearer passthrough, never a shared key), identical tool allowlist, launch_apply never auto-approved over MCP, no shell/file tools.
  • Not adopted: replacing in-process tools with MCP (latency + auth complexity for zero user-visible gain); extension-as-MCP-server before the worker plane proves out.

18. Native Gemini Function-Calling Bridge & Tool ReAct Loop (Rev 10)

Forensic analysis identified the failure mode preventing Microsoft Agent Framework (MAF) from autonomously driving Aksh tools: AkshChatClientAdapter was calling IAiProvider.GenerateTextAsync(), which collapsed all history to the last user message, completely stripped ChatOptions.Tools, and returned string text without emitting FunctionCallContent. Because MAF never received tool calls, the ReAct loop never triggered.

GeminiFunctionCallingClient

Translates MEAI ChatOptions.Tools to Gemini functionDeclarations. Omitted when no tools are present (preventing Gemini 400 Bad Request). Multi-turn functionResponse parts are normalized to role: "user" per Gemini REST specifications. Returned functionCall parts are parsed via JsonDocument into typed CLR primitives and emitted as FunctionCallContent.

True Autonomous ReAct Loop

With AkshChatClientAdapter returning FunctionCallContent, MAF's HarnessAgent dispatches in-process AIFunctions (scrape_job, prepare_package, launch_apply), appends FunctionResultContent, and cycles back to the model until execution converges. 91 unit tests verify end-to-end tool calling.
